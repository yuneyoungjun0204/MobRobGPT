# 논문_그래프 — 평가 도판 모음

이 폴더의 그림은 **전부 `run_eval.py` 가 생성한다.** 손으로 만들거나 고치지 않는다.
숫자를 바꾸려면 평가를 다시 돌린다 — 그림만 고치면 CSV 와 어긋나 논문이 거짓이 된다.

```powershell
# 로컬(Ollama)과 GPT 를 동시에 — 지휘관 비교 축까지 나온다
python run_eval.py --backends ollama,openai --seeds 30 --replan-every 4

# LLM 없이 기동 계층만 (API 불필요, 빠름)
python run_eval.py --skip-llm --seeds 30

# 이미 돌린 CSV 로 그림만 다시
python run_eval.py --from-csv results/eval/episodes.csv
```

원자료·표는 `results/eval/` 에 남는다(git 미추적). 이 폴더의 그림만 추적한다.

## 지표 — 다섯 관점

포획률 하나로는 "그물을 퍼부어 올린 것 아닌가", "배가 부딪히지 않았나"에 답할 수 없다.
그래서 다섯 관점으로 나눠 전부 같은 방식(대응표본 CI)으로 낸다.
**↑ = 높을수록 좋음, ↓ = 낮을수록 좋음.**

| 관점 | 지표 | 뜻 |
|---|---|---|
| 방어 성과 | `capture_rate` ↑ | `N_cap/(N_cap+N_brc)` |
| | `breaches` ↓ | 모선까지 뚫린 적 수 |
| 안전 | `collision_rate` ↓ | **아군끼리 + 모선 충돌**, 척당 건수 |
| | `net_touches` ↓ | 아군이 설치된 그물에 걸림 |
| 자원 효율 | `nets_per_capture` ↓ | **적 1척 잡는 데 쓴 그물** — 적을수록 효율적 |
| 기동 비용 | `traveled_per_capture` ↓ | 포획 1척당 팀 총 이동거리 |
| | `turn_sum_rad` ↓ | 총 선회량(궤적 부드러움) |
| 교전 품질 | `cap_dist_mean` ↑ | 포획 지점의 모선 이격 — **공간축 조기 제압**(멀리서 잡음) |
| | `cap_time_mean` ↓ | 평균 포획 시각(step) — **시간축 조기 제압**(빨리 잡음) |
| | `net_deploy_edist` ↓ | **그물 전개를 시작한 순간 가장 가까운 적까지 거리.**<br>그물은 물에 고정되지 않고 표류하므로 **적에 붙여 뿌릴수록 유리** |

조기 제압을 **거리축·시간축 둘 다** 재는 이유: 멀리서 잡아도 늦게 잡으면 다음 파를 못 막고,
빨리 잡아도 모선 코앞이면 여유가 없다. 한쪽만 보면 결론이 뒤집힐 수 있다.

`nets_per_capture`·`traveled_per_capture` 처럼 **포획 수로 나눈 지표**를 쓰는 이유:
총량만 보면 "아무것도 안 한 조건"이 가장 효율적으로 보인다. 성과당 비용이라야 비교가 선다.

## 읽는 법 — 오해하기 쉬운 지점

- **오차막대는 표준편차가 아니라 부트스트랩 95% CI** 다. 캡션에 반드시 명시한다.
- **`figB` 에서 CI 가 0 선을 지나면 그 조건은 baseline 과 다르다고 말할 수 없다.**
  평균이 높아도 마찬가지다. 그런 결과는 그렇게 쓴다.
- 조건 비교는 **대응표본**(모든 조건이 같은 시드 = 같은 전장)이다.
  그래서 `figD` 의 점들이 같은 전장에서의 직접 대결이 된다.
- `figG` 의 **폴백률이 0 이 아니면** 그 LLM 조건은 일부가 휴리스틱이다.
  `run_eval.py` 가 20% 를 넘으면 경고를 찍는다 — 그 상태의 수치는 "LLM 성능"이 아니다.
- 포획률은 `N_cap/(N_cap+N_brc)` 라 분모가 좁다. `resolved_frac`(교전 종결률)을
  같이 봐야 "적게 만나서 높은 포획률"을 걸러낼 수 있다.

## 시드 수

논문용은 **30 이상**을 권한다. 스모크 테스트(3~6 시드)의 CI 는 지나치게 넓어
어떤 조건도 유의하게 나오지 않는다 — 그건 효과가 없다는 뜻이 아니라 표본이 모자란 것이다.

실제로 8 시드에서 충돌률이 **악화**(d_z −0.40)로 보였다가 30 시드에서 **개선 방향**으로
뒤집힌 적이 있다. 적은 표본의 부호는 믿을 것이 못 된다.

## ⚠ 재현 시 반드시 확인할 것 — 실제로 밟은 함정들

전부 **에러 없이 조용히 틀린 답을 내는** 종류다. 코드에는 가드를 넣었지만, 결과를 쓰기 전에
사람 눈으로도 확인할 것.

### ① 재계획 주기의 단위 (가장 위험)

`--replan-every` 는 **결정(decision) 단위**다. 배포 경로 `run_commander_ui.py --replan N` 의
N 은 **step 단위**다. `decision_period=25` 이므로:

```
--replan-every 1  ==  배포의 --replan 25   ← 기본값. 이게 배포 설정과 같다
--replan-every 4  ==  배포의 --replan 100  ← 계획이 4배 낡는다
```

휴리스틱 배정(`_compute_assignment`)은 **매 결정** 새로 계산된다. 그래서 `replan-every>1` 로
두면 'LLM 대 휴리스틱'이 아니라 **'낡은 LLM 계획 대 최신 휴리스틱'** 을 비교하게 된다.
API 비용을 아끼려고 올리면 그대로 LLM 에게 불리한 편향이 된다.

원자료에 `replan_every` 컬럼이 있으니 **집계 전에 값이 하나인지 확인**하라.
값이 섞여 있으면 서로 다른 조건을 한 표에 넣은 것이다.

### ② 커버리지 불균형

평가가 중간에 끊기면 조건마다 덮은 포메이션이 달라진다. 그 상태로 평균을 내면
'쉬운 포메이션만 돈 조건'이 유리해진다. `coverage.csv` 를 보고 숫자가 고른지 확인하라.
집계는 `stats.balanced_subset()` 이 공통 교집합만 쓰도록 막아 두었고, 불균형이면 경고가 뜬다.

### ③ 천장 효과

`concentrated` 포메이션은 휴리스틱만으로 포획률 **0.997** 이 나온다. 여기서는 어떤 방법도
개선 여지가 없고 실수만 드러난다. **이 포메이션 단독으로 결론을 내지 말 것.**
판단은 `diversionary`·`wave` 를 포함해서 한다.

### ④ 체크포인트 append 시 열 순서

`episodes.csv` 는 에피소드 1건마다 append 된다. `to_csv(mode="a")` 는 값을 **자리로** 붙이므로
dict 키 순서가 파일 헤더와 다르면 열이 통째로 밀린다 — 실제로 `replan_every` 칸에 모델명이
들어간 사고가 있었다. 지금은 기존 헤더 순서로 재정렬해 쓰고, 새 컬럼이 생기면 세운다.
**지표를 추가하면 기존 CSV 를 이어받지 말고 `--no-resume` 으로 새로 시작할 것.**

### ⑤ LLM 폴백

지휘관 초기화에 실패하면 `plan()` 이 조용히 휴리스틱을 돌려준다 — 그러면 'LLM 조건'이
사실상 휴리스틱이 된다. `run_eval.py` 가 시작할 때 세우고, 폴백률 20% 초과 시 경고한다.
`llm_metrics.csv` 의 `fallback` 열이 0 인지 확인하라.

### ⑥ 배정 권한 모드

기본 `mode="llm"` 은 **순수 LLM 배정**이다(`commander/sim_bridge.py:372`). 코드 보완이 전혀
없어 LLM 이 비워 둔 클러스터는 담당 없이 남는다. 이건 논문의 설계 의도(조합최적화 후처리
없음)이지 버그가 아니다 — 다만 LLM 조건에 불리하게 작용하므로 해석할 때 감안할 것.
